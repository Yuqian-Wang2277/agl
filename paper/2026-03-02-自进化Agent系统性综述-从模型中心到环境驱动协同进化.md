## 摘要提炼

当前 LLM 最根本的局限是**静态性**：模型参数在部署后无法根据新任务、新知识或动态交互上下文自动调整。这篇综述是**首篇系统全面聚焦自进化 Agent** 的论文，围绕四个核心维度构建统一框架：

| 核心问题 | 包含内容 |
|---------|---------|
| **What** to evolve：进化的是什么？ | 模型、上下文、工具、架构 |
| **When** to evolve：何时进化？ | 测试中（intra）vs 测试间（inter） |
| **How** to evolve：如何进化？ | 奖励驱动、示范模仿、种群进化 |
| **Where** to evolve：在哪里进化？ | 通用领域、编程、GUI、金融、医疗、教育 |

**核心主张**：自进化 Agent 代表了从「扩展静态模型」到「发展自进化 Agent」的范式转变，是通往 ASI（人工超级智能）的关键中间阶段。

---

## 一、为什么需要自进化 Agent？

进化路径：LLM（静态推理）→ Foundation Agent（工具+规划）→ Self-Evolving Agent（持续自我进化）→ ASI（未来目标）

传统方法的局限：
- **SFT/RL**：依赖人类工程师策划数据并安排更新计划，非自主
- **RAG**：只能检索知识，不能真正改变推理策略
- **静态 Agent**：面对开放动态环境时持续失效

**自进化 Agent 的操作性定义**（三个必要条件）：
1. 更新必须**依赖经验**（轨迹、自生成数据、环境反馈），针对 Agent 的策略局限
2. 更新必须产生**持久的策略变化**，而非只是短暂的指令跟随
3. 系统必须具备**自主探索或自发学习**机制

## 二、形式化定义

### 2.1 环境：POMDP 框架

环境被形式化为 E = (G, S, A, T, R, Omega, O, gamma)：
- **G**：目标集合（用户查询）
- **A**：动作空间 = 自然语言 union 工具调用
- **R: S × A × G → R**：反馈函数（标量或文本，可来自外部环境或内部信号）

### 2.2 Agent 系统

Pi = (Gamma, {psi_i}, {C_i}, {W_i})：
- **Gamma**：架构/控制流（图或代码结构）
- **psi_i**：底层 LLM
- **C_i**：上下文（prompt + memory）
- **W_i**：工具集

### 2.3 自进化策略（核心定义）

```
f(Pi, tau, r) = Pi'
```

f 将当前 Agent 系统、执行轨迹 tau 和反馈 r 映射为新状态 Pi'。

**目标**：最大化跨任务序列的累积效用：

```
max_f  sum_{j=0}^{n} U(Pi_j, T_j)
```

关键区别在于：传统方法中，人类工程师定义 f；自进化 Agent 中，f 本身由 Agent 根据经验**自主决定**。

## 三、What to Evolve：进化什么？

论文将 Agent 的进化对象分为四个核心支柱：

```
+--------------------------------------------------+
|              自进化 Agent 的四大进化支柱           |
+------------+-----------+----------+--------------+
|  模型(M)   | 上下文(C) | 工具(T)  |  架构(A)     |
|            |           |          |              |
| 策略参数   | 记忆演化  | 自主创建  | 单Agent优化  |
| 经验积累   | Prompt优化 | 迭代精炼 | 多Agent协同  |
|            |           | 规模管理  |              |
+------------+-----------+----------+--------------+
```

### 3.1 模型进化（Model Evolution）

**策略（Policy）**——通过自生成数据持续微调参数：

| 方法 | 核心机制 |
|------|---------|
| SCA（Self-Challenging Agent） | 交替生成 Code-as-Task 问题并求解，用成功轨迹微调自身 |
| Self-Rewarding LM | 模型同时作为自己的奖励函数，生成自包含训练数据 |
| TextGrad | 将非结构化文本反馈视为可微训练信号，同时影响 prompt 和参数 |
| AutoRule | 将推理轨迹和偏好反馈转化为显式规则奖励，指导 RL 更新 |

**经验（Experience）**——通过环境交互积累经验驱动进化：
- **Reflexion**：自然语言"口头强化学习"，将失败反思存入情节记忆指导未来
- **AgentGen**：生成完整仿真环境（PDDL/Gym），实现双向进化课程
- **RAGEN**：将多轮工具使用建模为 MDP，用稠密环境奖励持续优化策略

### 3.2 上下文/记忆进化（Context Evolution）

**记忆演化**——从一次性经验到长期能力积累：

具体轨迹 → 抽象规律（heuristics，如 Expel）→ 可复用工作流（如 Agent Workflow Memory）

典型系统：
- **Mem0**：两阶段管道——提取关键事实 → ADD/MERGE/DELETE 操作管理长期记忆
- **Memory-R1**：用 RL 专门训练 Memory Manager Agent 学习何时增删改查记忆
- **Expel**：从过去轨迹提取洞察和规则，经验越积累性能越高
- **ReasoningBank**：将成功和失败经验蒸馏为可复用推理策略，引入记忆感知的测试时扩展

**Prompt 优化**——将 prompt 文本本身作为可学习参数：
- **APE**：生成候选 prompt，验证集评分选最优
- **PromptBreeder**：维护种群，以自引用方式不断进化更有效的指令
- **SPO**：完全自包含循环——自生成训练数据 + 偏好比较 → 精炼 prompt，零外部标注

### 3.3 工具进化（Tool Evolution）

工具进化遵循"创建 → 精炼 → 管理"三阶段：

- **Voyager**（Minecraft）：探索试错构建不断扩展的技能库，无监督
- **CREATOR**：解耦抽象工具创建（推理函数通用结构）与具体工具使用（如何应用），提升复用性
- **SkillWeaver**：分析成功轨迹 → 合成可复用 API → 迭代确保质量
- **ToolGen**：将工具编码为 LM 词汇表中的独特 token，将工具检索重构为生成问题

工具精炼：从编译错误、API 返回值、环境状态变化等富集反馈信号中学习，精炼工具代码和文档。

### 3.4 架构进化（Architecture Evolution）

**单 Agent 系统优化**：

| 方法 | 核心思路 |
|------|---------|
| TextGrad | "文本梯度"反向传播，系统精炼每个节点的 prompt，无需修改拓扑 |
| AFlow | MCTS 搜索 agentic 工作流空间，自动发现优于人工设计的工作流 |
| Darwin Gödel Machine | Agent 直接修改自己的 Python 代码库，开放式递归自我改进 |
| AgentSquare | 模块化设计空间 + 进化算法发现规划器+记忆+工具的最优组合 |

**多 Agent 协同优化**：
- **ADAS**：将系统设计定义为图灵完备代码配置空间的搜索，MCTS 高效探索
- **AFlow**：引入可复用 agentic 模式算子，实现比人工设计更优的工作流
- **ReMA**：多 Agent RL，协同训练高层元思考者和低层执行者

## 四、When to Evolve：何时进化？

```
+------------------------------------------------+
|              进化时机的双轨分类                 |
+----------------------+------------------------+
| 测试中进化            | 测试间进化              |
| (Intra-test-time)   | (Inter-test-time)      |
+----------------------+------------------------+
| 实时耦合当前任务      | 任务完成后进行          |
| 优化当前实例性能      | 提取跨任务规律          |
| 受实时计算约束        | 可用更复杂的学习程序    |
+----------------------+------------------------+
```

### 4.1 测试中进化（Intra-test-time）

**ICL 方式**（无参数更新，靠上下文窗口实时适应）：
- **AdaPlanner**：区分 in-plan 反馈（按预期）和 out-of-plan 反馈（偏离），后者触发全局计划修订
- **Self-Refine**：多轮自我批评和修订循环，显著提高准确率，无需任何训练

**SFT 方式**（即时参数修改）：
- **Test-Time Self-Improvement (TT-SI)**：识别不确定测试样本 → 生成合成训练例 → 临时轻量参数更新 → 完成后重置权重

**RL 方式**（按需开发新能力）：
- **LADDER**：遇到极难问题 → 自动生成相关问题变体 → 密集 RL → 扩展能力边界

### 4.2 测试间进化（Inter-test-time）

**ICL 方式**（跨任务积累经验作为上下文）：
- **Agent Workflow Memory**：从行动历史中归纳工作流，在线评估累积成功率不断提升
- **In-Context RL (ICRL)**：维护观察-动作历史，Transformer 在前向传播中隐式执行 RL

**SFT 方式**（迭代自我提升）：
- **STaR**：生成推理链 → 微调正确解 → 循环迭代，无需真值推理路径
- **SELF**：先习得自反馈和自精炼能力，再迭代生成-增强-再训练
- **SiriuS**：维护正确解仓库 + 多阶段精炼失败尝试

**RL 方式**（广泛环境交互）：
- **WebRL**：自进化课程——失败时自动生成类似但可管理的任务（4.8% → 42.4%）
- **DigiRL**：设备控制 Agent 通过自主强化学习掌握真实交互

## 五、How to Evolve：如何进化？

### 5.1 奖励驱动进化（Reward-based Evolution）

奖励类型分类：
- 文本反馈（Textual）：Reflexion, Self-Refine, AdaPlanner
- 内部置信度（Internal）：CISC, Self-Rewarding LM, 自我一致性
- 外部奖励（External）：环境反馈, 规则奖励, 多数投票
- 隐式奖励（Implicit）：next-token prediction 内置奖励信号

**关键 Reward 设计范式对比**：

| 类型 | 优点 | 局限 | 代表方法 |
|------|------|------|---------|
| 文本反馈 | 细粒度、可解释 | 需要强大的评判 LLM | Reflexion, TextGrad |
| 内部置信度 | 无需外部监督 | 可能存在自信偏差 | Self-Rewarding LM, CISC |
| 外部规则 | 客观可靠 | 只适合有明确验证的任务 | RAGEN, 数学/代码任务 |
| 隐式奖励 | 利用预训练内置信号 | 解释性差 | PIT, Endogenous Reward |

**过程奖励 vs 结果奖励**（核心发现）：

过程奖励比结果奖励更可靠，提供更稠密的学习信号。Math-Shepherd 用 MCTS 自动标注步骤级监督：

```python
# Math-Shepherd 核心思路（伪代码）
def auto_process_reward(step, problem, n=100):
    # 用 MCTS 估计该步骤能到达正确答案的概率
    success_rate = mcts_rollout_from_step(step, problem, n_samples=n)
    return success_rate  # 步骤级奖励信号，自动生成密集监督
```

**混合奖励设计**（GiGPO）：片段级结果奖励 + 步骤级局部奖励，解决长程任务稳定性和信用分配问题。

### 5.2 模仿与示范学习（Imitation & Demonstration Learning）

核心特点：利用高质量示范轨迹，无需设计奖励函数。

自生成示范学习的基本循环（以 STaR 为原型）：

```
模型尝试解题 → 生成正确/错误解 → 过滤正确轨迹（+为错误题生成后见推理链）
    ↑                                          |
    +--------------- 微调模型 ←---------------+
（循环迭代，性能不断提升）
```

代表方法：
- **V-STaR**：引入验证者模型，评估生成推理链质量后再纳入训练
- **SiriuS**：多 Agent 互相学习，系统维护全局经验库（off-policy 高效复用）
- **RISE**：递归自我提升，结合反思、多阶段精炼和改写

### 5.3 种群进化（Population-based & Evolutionary Methods）

**自我博弈（Self-Play）**——关键范式：

| 方法 | 角色设计 | 核心机制 |
|------|---------|---------|
| Absolute Zero | Challenger + Solver | Challenger 生成边界问题，Solver 求解；零数据自举 |
| SPIN | 当前模型 vs 历史版本 | 竞争历史版本产生进化压力 |
| SPC | 偷偷犯错的生成者 vs 批评者 | 对抗游戏，生成欺骗性错误，批评者学会检测 |
| Socratic-Zero | Solver + Teacher + Generator | 三方协同：Teacher 出题，Generator 蒸馏策略 |
| SCA | Challenger + Executor（同一模型）| 交替出题/解题，用成功轨迹微调自身 |

**遗传/进化算法**：
- **DGM（Darwin Gödel Machine）**：维护所有历史版本存档，可从任意过去版本分支，开放式演化
- **GENOME**：将遗传算法直接应用于模型参数（交叉/变异/选择），无需梯度

### 5.4 三大进化范式对比

| 维度 | 奖励驱动 | 模仿学习 | 种群进化 |
|------|---------|---------|---------|
| 反馈类型 | 标量/文本/置信度 | 示范轨迹/范例 | 适应度分数/竞争信号 |
| 样本效率 | 中等（取决于奖励稀疏性） | 高（示范质量高时） | 低（需大量试验） |
| 稳定性 | 对奖励设计敏感 | 对示范质量/多样性敏感 | 对种群规模/多样性敏感 |
| 可扩展性 | 自动化时良好 | 受示范收集成本限制 | 高但资源密集 |
| 适用场景 | 有明确反馈的任务 | 高质量示范易得的任务 | 需要结构性创新的任务 |

## 六、Where to Evolve：应用领域

### 6.1 通用领域进化三种核心机制

## 七、评估体系设计（重点）

### 7.1 五维评估目标

```
+----------------------------------------------+
|           自进化 Agent 五维评估框架           |
+----------------------------------------------+
| 适应性 (Adaptivity)    | 随交互历史的性能改进 |
| 保留性 (Retention)     | 灾难性遗忘的抵抗能力 |
| 泛化性 (Generalization)| 跨域迁移和 OOD 能力  |
| 效率   (Efficiency)    | 计算/token/时间成本  |
| 安全性 (Safety)        | 行为对齐和有害性控制 |
+----------------------------------------------+
```

传统评估只测快照性能，自进化 Agent 需要追踪**随时间演化的学习轨迹**——这是评估范式的根本性转变。

### 7.2 关键评估指标

**遗忘与迁移**（Retention 核心指标）：

设 J_{i,t} 为完成第 t 个任务后在任务 i 上的性能：

```
FGT_t = (1/(t-1)) * sum_{i=1}^{t-1} [max_{j in {i,...,t}} J_{i,j} - J_{i,t}]
（遗忘量：FGT > 0 表示发生遗忘）

BWT_t = (1/(t-1)) * sum_{i=1}^{t-1} (J_{i,t} - J_{i,i})
（回溯迁移：BWT > 0 表示新学习正向迁移到旧任务）
```

**效率指标**：

```
CPG_t = Total_Cost_t / (Performance_Gain_t + epsilon)
（每单位性能提升的代价，越低越好）

TP_$ = Delta_score / sum_i cost(tool_i)
（工具生产力：每单位工具调用成本带来的性能增益）
```

### 7.3 Prompt / Reward / Evaluation Metric 设计要点

#### Prompt 设计关键洞察

- **多节点系统需联合调优**：DSPy 将整个工作流表示为图，联合优化各节点的子 prompt
- **文本梯度**（TextGrad）：将文本反馈视为"可微"训练信号，可反向传播至每个节点
- **SPO 完全自包含**：通过偏好比较完全消除对外部标注的依赖，实现真正的 prompt 自进化

#### Reward 设计关键洞察

- **过程奖励 > 结果奖励**：提供更稠密的学习信号，有效解决信用分配问题
- **混合奖励**（GiGPO）：片段级 + 步骤级双重校正，解决长程任务稳定性问题
- **隐式奖励**：LLM 的 next-token 预测本身内置了奖励信号，可通过 logits 直接提取
- **避免奖励黑客**：需要多样化验证，防止 Agent 利用奖励漏洞（"Alignment Tipping Process"）

#### Evaluation Metric 设计关键洞察

- **必须追踪时间轨迹**，而非单次快照
- **明确报告自主程度**：进化策略是预定义的、程序采样的还是 Agent 自主生成的
- **明确报告反馈来源**：外部人类标签、规则评估器还是自生成反思
- **引入 FGT/BWT/CPG**：这些指标专为自进化设计，能区分真正自进化与外部引导

### 7.4 评估范式三层次

| 范式 | 时间范围 | 适合评估 | 代表基准 |
|------|---------|---------|---------|
| 静态评估 | 单次快照 | 适应性（基线） | SWE-bench, WebArena |
| 短程自适应评估 | 有限迭代（同类任务） | 适应性、效率 | MemoryAgentBench |
| 长程终身学习评估 | 跨域任务序列 | 保留性、泛化性、安全性 | LifelongAgentBench |

**代表性基准**（完整列表摘录）：

## 八、安全与未来方向

### 8.1 自进化特有的新风险

| 风险类型 | 机制描述 | 缓解策略 |
|---------|---------|---------|
| 行为漂移（Misevolution） | 自训练数据侵蚀安全对齐；"Alignment Tipping Process"使对齐 Agent 转向违规行为 | 持续红队测试 + 对齐漂移监控 |
| 奖励黑客 | 开放进化下 Agent 利用内部奖励信号漏洞（如记忆积累诱发不当行为）| 奖励健壮性检测 + 指标异常告警 |
| 工具安全 | 自创工具可能含安全漏洞或触发隐私泄露 | 强制沙箱执行 + 自动漏洞扫描（SAST）|
| 记忆中毒 | 有害记忆潜移默化影响未来决策 | 双记忆结构 + 共识验证（A-MemGuard）|

**重要发现**：自主进化程度越高，安全风险越大。WebRL 将成功率从 4.8% 提升至 42.4%，但另有研究显示对齐欺骗率从 12% 升至 78%（当 Agent 在冲突目标下自主进化时）。

### 8.2 合规部署检查清单（核心条目）

工具与代码安全：
- 严格沙箱：所有工具在隔离环境执行，无默认网络/文件系统访问
- 自动漏洞扫描：新工具上线前强制 SAST 扫描

自我修改控制：
- 不可篡改审计日志：所有自修改（参数/记忆/工具/逻辑）均可追溯
- 版本控制与回滚：保留已知安全快照，回滚机制定期测试
- 预更新安全验证：安全关键 prompt 集评估，防止对齐遗忘

行为与对齐安全：
- 持续运行时监控：检测偏离预期行为的异常
- 奖励黑客检测：关键指标异常变化触发告警
- 自动红队：持续生成测试场景探测新出现的错位

### 8.3 三大未来研究方向

1. **个性化 Agent**：冷启动问题、长期记忆管理、隐私保护的三角平衡；需要 Personal Adaptation Gain 等新指标
2. **泛化性**：专化 vs 通用性权衡、灾难性遗忘、知识跨 Agent 可迁移性
3. **多 Agent 生态**：集体 vs 个体推理平衡、动态角色分工、长程协同的动态评估基准

## 九、结论

这篇综述建立了自进化 Agent 的**第一个系统性框架**：

1. **理论框架**：用 POMDP + Agent 系统的形式化定义，精确刻画自进化策略
2. **四维进化支柱**：模型、上下文、工具、架构——全面覆盖进化对象
3. **双时序分类**：测试中 vs 测试间进化——澄清了大量此前概念混乱
4. **进化方法三范式**：奖励驱动/模仿学习/种群进化——各有利弊，互补使用
5. **评估体系**：五维目标 + 三层评估范式 + 专用指标（FGT/BWT/CPG）

**关键结论**：解决灾难性遗忘、人类偏好对齐、Agent 与环境协同进化，是通往真正自进化 Agent 的关键挑战。

## 十、对我们项目（Agent Lightning）的启发

### 项目背景

我们的项目核心机制：**让模型从 few-shot 示例中提取解题策略，再应用策略解决新问题**。

这与论文中的多个关键方向直接对应——我们当前的架构属于论文所说的"原型进化（proto-evolution）"形态，具备从上下文中自适应提取策略的能力，但尚未形成持续积累的进化循环。

### 可直接借鉴的方向

**1. 策略记忆进化（Memory Evolution for Strategy Reuse）**

Expel、ReasoningBank、Agent Workflow Memory 都证明了：将过去经验蒸馏为**可复用的高层策略/规则**，比直接检索具体轨迹更有效，且积累越多性能越好。

我们的升级路径：
- 自动积累历次解题成功的"策略"到策略库（StrategyBank）
- 用 ADD/MERGE/DELETE 操作持续精炼，删除低效策略，合并相似策略
- 按任务类型分类管理，支持语义检索（从 few-shot 检索变为策略检索）
- 追踪哪些策略在 OOD 问题上泛化（对应论文的 Generalization 维度）

**2. 自我博弈强化策略质量（Self-Play for Strategy Validation）**

Absolute Zero、SCA 展示了 Challenger-Solver 架构的威力：出题者和解题者协同进化，自动找到能力边界。

我们可以引入：
- 让模型生成"测试用例"来验证提取出的策略是否真正泛化（策略验证器）
- 策略提取端（Challenger）和策略应用端（Solver）协同进化
- 用成功/失败的应用结果**反向改进**策略提取过程本身

**3. 过程奖励指导策略选择（Process Reward for Strategy Ranking）**

在策略应用的每个推理步骤上给出奖励信号（该步是否符合策略逻辑），比只看最终答案更有价值——这与 Math-Shepherd 的步骤级自动标注思路完全对应。

**4. 测试中策略修正（Intra-test-time Strategy Refinement）**

当前框架：few-shot 示例 → 提取策略 → 应用（一次性）。

可引入**测试中策略修正**：遇到环境反馈（执行错误、中间结果不符合策略预期）时，即时调整策略解读，生成修正后的策略指导后续步骤（类似 AdaPlanner 的 out-of-plan 修订机制）。

**5. 评估体系借鉴**

- **适应性**：策略提取质量随 few-shot 样本数增长的曲线（学习曲线）
- **泛化性**：提取的策略在新问题类型（OOD 分布）上的迁移效果
- **效率**：每次成功应用策略消耗的 token 数（CPG 思路）
- **保留性**：策略库积累是否导致旧问题类型策略退化（FGT 指标）

### 一句话概括

> 这篇综述为我们指明了升级路径：**当前的 few-shot 策略提取是自进化 Agent 的"原型形态"，下一步应将策略库构建为可持续积累、自动精炼、跨任务迁移的"记忆进化引擎"，并引入 Challenger-Solver 自博弈机制提升策略质量上限**——直接对应论文从「模型中心进化」到「记忆+工具协同进化」的核心演进方向。
